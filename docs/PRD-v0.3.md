## 1. 产品定位与第一期范围

### 1.1 已确认的产品边界

软件是单机桌面三维建筑编辑器，不依赖云端账号或在线服务完成核心工作。主要操作直接发生在三维场景中，不要求用户先完成二维图纸，也不要求用户理解顶点、面片、布尔运算或 UV 展开。

第一期以“创建容易、修改直观、贴图正确、保存可靠、导出可用”为目标。宁可减少对象种类和高级选项，也不能用难操作的交互或错误几何代替基础能力。

| 模块 | 已确认要求 | 第一阶段边界 |
| --- | --- | --- |
| 建筑与楼层 | 支持多层；通过楼层列表选择当前层 | 其他楼层半透明、不可交互；首期不要求楼层实际连通 |
| 墙体 | 创建有厚度的墙体；本期直角连接 | 架构必须保留任意角度能力 |
| 楼板 | 矩形、有厚度；上下表面均可设置贴图 | 保留多边形能力；顶层封板由用户控制 |
| 门 | 自动门洞、门框、门板；支持开关与旋转支点 | glTF 必须包含可播放的开关动画；门型与默认角度采用建议方案 |
| 窗户 | 自动开洞、窗框、玻璃 | 采用内置简洁设计 |
| 墙面材质 | 正反面可用不同图片，重复平铺 | 顶、底、端面及门洞内侧为纯色 |
| 材质来源 | 本地图片与内置材质 | 相邻墙面纹理应连续对齐 |
| 文件 | 保存、重新打开本地项目；导出三维模型 | 导出符合 glTF 2.0，包含门开关动画 |
| 技术与语言 | Tauri 2.0 技术路线、Three.js、React + TypeScript 前端、Rust 后端 | Windows、macOS；英语、简体中文 |
| 开发 Skills | Anthropic frontend-design、Impeccable、Vercel Composition Patterns | 项目实施时安装、验证可用并按第 9.4 节执行 |
| 前端架构 | React UI + 同页面原生 Three.js + 独立 EditorCore | 单主窗口、单 WebView、单主 Canvas；不采用 iframe／R3F |
| 主题 | 跟随系统、亮色、暗色 | 保存用户选择；系统模式动态响应系统变化 |
| UI 基础设施 | packages/ui 统一导出全部 UI 颜色 token；组件采用 shadcn/ui | 双主题语义 token；共享组件、主题能力与导出入口 |

### 1.2 已确认的范围排除与其他建议

**已确认：第一期不需要楼层之间实际连通。** 不实现用于跨层通行的楼梯、坡道、电梯和楼板连通开洞；多层搭建、楼层切换、保存与导出不能以具备这些设施为前提。墙体上的门窗洞口仍属于第一期必需能力，不受本项排除影响。

**其他建议排除项：** 不主动增加家具商城、账号、云协作、AI 生成、真实物理模拟、复杂渲染、建筑结构分析、专业施工图、自由网格编辑和外部模型导入。任意角度墙体及多边形楼板仅保留扩展能力，不提前实现完整操作界面。

门开关动画导出、用户控制的顶层封板、系统／亮色／暗色主题，以及本版架构与 UI 基础设施均属于第一期。主题颜色自定义编辑器、在线主题市场和多窗口编辑不主动纳入。其余未决事项仅保留在第 13 节。

## 2. 必须统一的对象和空间定义

### 2.1 楼板与天花板：一个对象、两个独立表面

**建议方案：在数据中统一称为“楼板”，在界面中显示“上表面（地板）”与“下表面（天花板）”。** 两个表面可以分别选图片、纯色及平铺尺寸，修改一面不改变另一面；四周厚度面建议统一使用可调纯色。

例如，二层楼板的上表面可以是二层木地板，下表面可以是一层白色天花板。它只是一块实体，不应再创建一块与下表面重合的“天花板模型”。

建议楼板归其上表面所在楼层管理。二层楼板即使从一层看起来是天花板，仍属于二层。在一层编辑时不能直接选中它；需要切换到二层，再从楼板属性中修改“下表面”。这与“非当前层不可交互”保持一致。

顶层封板由用户决定是否创建、保留或删除。没有封板就保持敞开；软件不自动补板，不在保存、重新打开、切层或导出时擅自封顶。封板复用有厚度楼板及上下独立材质的能力，具体交互建议见第 4.6 节。

### 2.2 标高、层高、墙高不得混为一谈

建议使用米作为内部长度单位，以 Y 为竖直轴，XZ 为水平编辑平面。glTF 2.0 使用米作为线性距离单位及 Y 向上的坐标约定，因此导出时必须保持单位与轴向一致。[R6]

建议“楼层标高”定义为该层默认楼板上表面的高度，板厚向下延伸。层高表示相邻楼层参考面的高度差，墙高表示墙体实际高度，二者分别保存。

示例：一层标高 0 m，二层标高 3 m，二层板厚 0.2 m，则二层楼板下表面位于 2.8 m。需要贴合它的一层墙高为 2.8 m，而不是默认把 3 m 层高直接当成墙高。

建议修改层高时，显示将整体移动的上方楼层并统一提交；已有墙高不静默改变。第一期不增加复杂自动结构约束求解，但必须明确标高与墙板接触关系，不能产生不提示的穿插。

### 2.3 墙体的“正反面”采用稳定的面身份

墙体大面在数据中建议使用稳定的 A 面、B 面标识，不自动推断“室内面、室外面”。界面选中面时应高亮，并允许通过属性面板切换 A/B 面。

A/B 面身份不得因相机转到另一侧、墙体重新生成、门窗开洞或端点数据重排而交换。正面和反面是实体的两个不同外表面，不是同一张薄面开启双面渲染。[R6]

## 3. 核心交互方案

### 3.1 页面布局

采用单主窗口、单三维视口；React UI 与原生 Three.js Canvas 位于同一 WebView 页面，视觉一体、模块分离。顶部放置“选择、墙体、楼板、门、窗、材质”和保存、撤销、导出等常用操作；左侧是楼层列表；右侧是当前选择对象的属性；底部显示当前工具、操作提示及尺寸。

不默认展示大量专业面板。工具使用文字与图标共同表达，不只依赖图标。选中墙体就只展示墙体有关的属性，选中门才展示开关与支点有关的属性。

### 3.2 相机与建模输入分离

建议左键负责选择、放置和编辑；右键拖动旋转视角，Shift 加右键拖动平移，滚轮缩放。macOS 必须同时提供可用的触控板操作及“旋转／平移”视口按钮，不依赖中键才能完成任务。

提供“聚焦选中”“查看当前层”“查看整栋”按钮，避免用户迷失。可以提供俯视快捷视角，但它仍属于同一个三维编辑环境，不新增独立二维编辑流程。

绘制过程必须可暂时操作相机，恢复后保留当前预览。Esc 取消尚未提交的预览或退出当前工具，不能撤销此前已经完成的墙段；撤销按钮负责撤销已提交操作。

### 3.3 最短操作路径

| 任务 | 建议操作路径 | 完成后的状态 |
| --- | --- | --- |
| 创建墙段 | 选择墙体 → 点起点 → 点终点 | 创建实体，可继续接下一段 |
| 创建矩形楼板 | 选择楼板 → 点两个对角点 | 生成有厚度的实体 |
| 创建顶层封板 | 楼板工具选择“顶层封板” → 确认高度 → 点两个对角点 | 按用户指定范围封顶，可选中修改或删除 |
| 放置门窗 | 选择门／窗 → 在当前层墙面预览 → 单击 | 自动开洞并放置构件 |
| 修改尺寸 | 选中对象 → 输入尺寸或拖动专用控制点 | 预览后统一提交 |
| 更换一面贴图 | 选择目标面 → 选择内置材质或本地图片 | 只改变该目标面 |
| 开关门 | 选中门 → 点击打开／关闭 | 门板绕铰链转动，门框不动 |
| 切换楼层 | 点击楼层列表中的一层 | 该层可编辑，其余层半透明且禁用交互 |
| 切换主题 | 打开设置中的外观 → 跟随系统／亮色／暗色 | 即时应用并记住选择，不重载场景或修改建筑 |

### 3.4 选择、修改与撤销

单击选择对象；材质工具下单击选择具体表面。点击门是选择门，不立即触发开门，避免选择与播放冲突。

墙体提供端点及沿允许方向的移动操作；门窗沿宿主墙移动；楼板在当前楼层平面移动、调整矩形大小。尺寸输入始终显示单位。不得默认把自由三轴变换手柄作为所有对象的唯一编辑方式。

建议至少支持创建、删除、位置修改、尺寸修改、贴图修改、楼层修改及门角度修改的撤销与重做。一次拖动是一条历史记录；门动画每一帧、鼠标预览和临时高亮不进入历史。

非法操作应保留原有对象，说明具体原因，例如“门洞超出墙体边界”，不能静默修正成另一个位置。删除墙体时提示其附属门窗将一起删除；撤销必须完整恢复关联对象。

## 4. 建筑对象功能需求

### 4.1 F-01 楼层管理

支持新增、重命名、选择、删除楼层，以及设置楼层高度相关参数。每个建筑对象必须属于一个明确楼层。新建对象默认属于当前层，并使用该层编辑平面；顶层封板使用其显式设置的高度。新增楼层不自动生成楼梯或楼板连通洞口。

其他楼层采用编辑器临时半透明显示，不参与选择、拖动、贴图、吸附及门窗放置命中测试。不能仅降低透明度却仍让鼠标选中后方楼层。

楼层半透明不能写入模型的真实材质。建议提供整栋预览状态：恢复所有楼层真实外观，保留视角浏览与门开关预览，不进行几何编辑。

删除有内容的楼层必须显示影响范围并支持撤销。复制整层不是已确认能力，不作为完成多层建筑的前提。

### 4.2 F-02 墙体创建、连接和编辑

墙体以起点、终点、高度和厚度定义，绘制时预览实体厚度和长度。建议长度字段明确标为“轴线长度”，避免与墙内侧净长、外侧长度混淆。

本期新建及修改时限制为水平平面中的正交方向，支持共线延长和直角连接。建议至少覆盖直线、L 形转角及 T 形相接。十字交叉与异厚墙复杂连接的具体能力边界，应在几何原型中列明；未支持情况必须在提交前阻止并提示。

连接必须是真正的几何与拓扑关系，不能只把两个长方体叠在一起。已支持的连接处不得出现缝隙、闪烁、外露的内部端盖或突出的多余墙块。

调整墙长、高度或厚度后，应同步更新连接、门窗洞口与纹理。门窗仍须位于有效墙域；修改后无法容纳门窗时，应阻止提交并说明受影响对象，不静默删除或挤压门窗。

几何生成方式不在产品层面限定为布尔运算或分块三角化，但最终导出的墙体必须有真实洞口和正确表面。

### 4.3 F-03 矩形楼板

支持通过两个对角点创建矩形楼板，并设置长、宽、厚度和位置。楼板必须是有厚度的实体，不能使用仅有一面的平面替代。

上表面、下表面独立设置材质；四周厚度面按第 5 节的建议使用纯色。尺寸变化时，贴图的实际平铺尺寸保持稳定，不随模型整体拉伸。

建议支持对齐当前层墙体边界、端点与网格。矩形铺设范围由用户决定，不在第一期自动推断房间轮廓或自动铺满所有闭合区域。

### 4.4 F-04 门、门洞和旋转支点

采用简单单扇平开门作为建议首发门型。用户选中墙体上的位置后，软件生成矩形门洞、门框和门板；不要求用户手动做开洞或对齐模型。

建议提供洞口宽、高、距墙体参考端的距离、铰链侧、朝 A/B 侧开启、当前角度等属性。尺寸字段注明“洞口尺寸”，避免把洞口宽度与扣除门框后的净通行宽度混为一谈。

支点默认自动放置在门板一侧的铰链轴线上。界面提供左右铰链切换和开启方向切换，展示支点标记；不要求用户手动输入支点三维坐标。

门板绕竖直铰链轴转动；门框、墙体及洞口不动。建议提供打开、关闭按钮及角度滑杆，默认关闭为 0°、完全打开为 90°。这些角度是建议默认值，不限制后续调整。

门被移动或墙体发生有效修改后，洞口、门框、门板和支点必须保持一致。删除门时恢复原墙面；重新生成门洞不得打乱墙面材质或平铺位置。

本地项目必须保存门的当前角度、铰链侧、开启方向及可重新生成开关动画的参数；建议区分当前角度、关闭角度、完全打开角度和动画时长。移动门、改铰链侧、改变开启方向后，应更新动画绑定，不能仍然引用旧支点或旧轨迹。

**已确认：第一期必须将门的开关动画导出到 glTF 2.0，不能只导出静态姿态或一个支点。** 动画范围是门板绕铰链的旋转，不要求复杂动画编辑器、骨骼系统、真实碰撞、门锁、弹簧或复杂五金。详细交付与验收见第 8.4 节。

### 4.5 F-05 窗户和窗洞

采用简单矩形固定窗作为建议设计，包含真实窗洞、窗框和玻璃。建议提供洞口宽、高、窗台离地高度及沿墙位置。

窗框默认使用纯色，玻璃使用简洁透明材质；不以真实折射效果为第一期目标。窗洞内侧建议沿用门洞规则，使用纯色，不延续墙面图片。

窗体移动或调整尺寸后，同步更新墙体洞口；删除窗体后恢复墙体。窗洞之间、窗洞与门洞之间不得形成未经支持的重叠。第一期窗户无需开关结构，除非后续另行确认。

### 4.6 F-13 用户控制的顶层封板

**已确认：是否封顶由用户控制。** 用户可以创建、调整或删除顶层封板，不要求自动识别闭合房间，也不要求软件自动补齐整栋屋顶。

建议复用矩形楼板工具，提供“普通楼板／顶层封板”用途选择。封板属于用户选定楼层，使用单独的垂直位置，不需要为封顶虚构一个额外楼层。用户指定矩形范围、厚度和高度；可将下表面对齐墙顶。数据仍按楼板上表面标高存储，即上表面标高等于下表面标高加板厚。

封板上、下表面分别设置图片或纯色，四周厚度面沿用楼板材质规则。创建、修改及删除支持撤销重做，并随本地项目保存。增加上方楼层时不静默删除、复制或改变现有封板用途；需要调整时由用户操作。

导出严格反映正式模型：有封板就导出，没有封板就不添加。临时隐藏封板用于观察内部，不等于删除，也不应改变默认整栋导出的内容。第一期不增加坡屋顶、屋架、瓦片、自动屋顶生成等功能。

## 5. 材质与指定面贴图

### 5.1 F-06 面级材质规则

**核心要求：贴图属于指定表面，不属于整个长方体。纯色面依然正常显示，不等于透明、隐藏或删除。**

| 对象与表面 | 材质行为 | 状态 |
| --- | --- | --- |
| 墙体 A 面 | 独立图片／纯色；图片重复平铺 | 已确认 |
| 墙体 B 面 | 独立图片／纯色；可与 A 面不同 | 已确认 |
| 墙体顶、底及两个暴露端面 | 只使用纯色，不采样墙面贴图 | 已确认 |
| 门洞内侧厚度面 | 只使用纯色 | 已确认 |
| 窗洞内侧厚度面 | 沿用门洞规则，使用纯色 | 建议方案 |
| 楼板上、下表面 | 分别使用独立图片或纯色 | 双面可贴图已确认；独立槽位为建议方案 |
| 楼板四周厚度面 | 只使用纯色 | 建议方案 |
| 门板正反面 | 可复用墙体的独立双面材质规则；窄边纯色 | 建议方案 |
| 门框、窗框、玻璃 | 框使用纯色；玻璃使用预设透明材质 | 建议方案 |

墙体相接后，处于内部的端面不得形成可见的纯色窄条；“厚度面不贴图”不是允许墙缝存在的理由。

技术约束：生成网格必须保留表面角色与材质分组，重建洞口后仍然可以准确分辨大面、端面和洞口内侧。Three.js 的 BufferGeometry groups 可让同一几何体的不同部分使用不同材质，这可作为实现途径，而不是把六个面统一绑定同一个贴图材质。[R3]

### 5.2 F-07 内置材质与本地图片

内置少量适合建筑的材质即可，例如砖墙、墙面、木地板和地砖。内置纹理应适合重复平铺，随安装包提供，离线可用。内置资源发布前须确认可随软件分发并用于模型导出。

本地图片建议首期支持 PNG、JPEG。导入时展示预览，并允许设置“图片每次重复覆盖的实际宽度和高度”。图片复制为项目资源，不能只记住原始磁盘路径。

属性面板主要暴露材质、实际平铺尺寸、旋转和偏移；不暴露着色器代码或复杂节点。平铺尺寸应关联到表面／连续组的绑定，不能因修改一面而意外修改全项目所有使用同一图片的对象。

### 5.3 F-08 真实尺寸重复平铺

墙变长时应增加图案重复次数，砖块或木板的视觉尺寸不能跟着变宽；墙变高和楼板变大同理。

建议采用统一的纹理尺寸与 UV 规则。Three.js 的纹理平铺、偏移和旋转是可分别控制的属性；重复采样只解决图案循环，不自动解决两个对象的起点对齐。[R4]

支持“恢复默认平铺”操作。连续组内调整平铺参数时应提示影响范围并作为一次可撤销操作。

## 6. 相邻墙体纹理连续性

### 6.1 F-09 连续性的验收含义

对于实际相连、使用相同图片且平铺尺寸与方向一致的可见墙面，纹理应按同一套坐标连续延伸。不能仅保证材质名称相同，也不能让每段墙都从图片左上角重新开始。

共线墙段接缝两侧的砖缝必须对齐。直角转弯时，同一条连续可见墙面的图案应沿转角延续；墙面仍保持正常的直角法线，不要求转角两侧因光照不同而呈现完全相同亮度。

门窗洞口只是从连续墙面中减去一块区域，洞口左右与上方的剩余墙面保持原来的纹理坐标；洞口内侧使用纯色，不把墙面纹理绕进去。

墙体 A、B 两侧分别管理连续关系，不能为了其中一侧对齐而镜像、交换或破坏另一侧。

### 6.2 建议的实现约束

连续墙面使用稳定的连续组与参考点，保存图片、实际平铺尺寸、方向和起点偏移。水平方向沿实际可见墙面的累计距离展开，竖直方向使用共同高度参考。

直角处须考虑墙厚及内外角的实际表面长度，不能仅以墙体轴线长度累计。分段创建顺序、墙段被分拆、开洞、保存重新打开，以及网格重新生成，都不得随意重置纹理起点。

例如，第一段墙的有效表面长度为 2.4 m，图片每 0.5 m 重复一次，则末端位于第 4.8 次重复。后一段应从同样的 0.8 周期位置接下去，而不是回到 0。验收样例必须包含这类非整周期长度，避免用恰好整除的墙长掩盖错误。

### 6.3 必须说明的边界：闭环与图片自身接缝

导入的图片如果左右边缘原本接不上，软件只能保证跨墙坐标连续，不能自动把它变成无缝纹理。内置可平铺纹理与带编号测试纹理应分别用于验证。

对固定平铺宽度 P 的一般周期纹理，沿一圈闭合墙面累计长度 L 后，要回到同一图案相位，需要 L/P 为整数。非整周期时，“保持尺寸不变、不拉伸、整个闭环处处无收口”一般不能同时满足。这是约束推导，不是现有实现的测试结论。

建议允许在指定转角或门边保留一个可解释的收口位置，其余连接保持连续；但这涉及对“全部接缝无缝”的取舍，尚待确认。T 形分支的连续面走向也需按实际可见墙面确定，不能随意跨越分支继承纹理。

闭环收口策略未确认前，不能宣称所有闭合房间都已实现无条件全周无缝。

## 7. 本地项目保存

### 7.1 F-10 保存、打开、另存为

本地项目必须保留可编辑数据，而不仅是渲染结果。建议包含版本号、楼层、墙体连接、楼板及顶层封板参数、门窗宿主关系、门支点与角度、开关动画生成参数、面材质绑定、连续纹理组及资源清单。封板是否存在及其用途必须随项目保存，不能在加载时按当前最高楼层重新猜测。

本地项目与 glTF 导出是不同用途：前者用于继续编辑参数，后者用于在其他三维软件中使用。不能把导出 glTF 作为唯一的工程保存功能。

建议使用一个可搬运的项目容器，内部包含项目数据和贴图资源；具体扩展名在实现阶段确定。同一张图片可以按内容标识复用，避免无谓复制。

项目移到另一个目录，或从 Windows 拷到 macOS 后，图片不应丢失。删除最初导入的原始图片，也不应破坏已经保存完整的项目。

### 7.2 数据可靠性

支持未保存修改提示。关闭、切换项目或新建项目时，存在修改则允许保存、放弃或取消；取消操作保持原工程。

保存应先写临时结果并校验，再替换目标文件。写入失败不能损坏上一次有效保存，也不能弹出成功提示。另存为不得覆盖源工程，除非用户明确选择覆盖。

对损坏项目、不支持的版本、丢失资源、非法数据、磁盘空间不足等情况，给出明确错误。新版本字段不得被静默丢弃后覆盖回原文件。

自动备份与崩溃恢复可作为建议增强项，但不代替上述基础保存可靠性。

主题模式和语言偏好属于本机应用设置，与建筑工程数据分开保存。切换主题不生成建筑撤销记录、不标记工程为未保存；打开或迁移工程不能覆盖接收设备上的主题选择。

## 8. glTF 2.0 导出

### 8.1 F-11 导出形式

已确认要求为包含门开关动画的 glTF 2.0 三维模型导出。建议默认提供单文件 .glb，同时提供 .gltf 及其配套资源输出；实际产品菜单可以保持简洁。每一种提供给用户的导出形式都必须满足相同的动画交付要求，不能用格式选择绕过动画导出。

.glb 与 .gltf 都属于 glTF 2.0 的交付形式。Three.js 的 GLTFExporter 支持两种形式及动画参数，可作为导出基础；外部分离资源如何打包、落盘仍需由应用完整处理。[R5]

### 8.2 必须保持的模型信息

模型导出必须保持真实墙体和楼板厚度、真实门窗洞口、正反面独立材质、纯色厚度面与洞口内侧、平铺尺寸、跨墙对齐关系，以及门框、玻璃、用户创建的顶层封板和门开关动画。

建议保留“建筑 → 楼层 → 对象”的基本层级。门板应保留独立铰链父节点和正确局部变换，不能与门框或墙体合并成无法单独旋转的网格。

单位与轴向正确。图片资源应完整包含在 .glb 中，或使用随 .gltf 交付的相对路径，不引用用户本机临时文件、绝对路径或远程材质服务。

### 8.3 编辑器显示不能污染导出

默认导出整栋建筑的真实模型，不导出网格、吸附提示、选择描边、支点标记、尺寸标签和临时绘制预览。

其他楼层在编辑时半透明，不代表它们在导出模型中应该半透明。导出必须从真实模型与材质构建，不能直接把含临时覆盖状态的显示场景原样输出。

GLTFExporter 默认仅导出可见对象。应用应构建明确的导出对象集合，避免遗漏因编辑器状态隐藏的楼层，也不能为了包含隐藏楼层而把所有辅助对象一并导出。[R5]

亮暗主题下导出的建筑材质、贴图、几何及动画语义必须一致。视口主题背景、网格颜色、吸附标记、选中高亮不属于建筑材质，不写入导出；切换 UI 主题不能改变用于模型预览的灯光强度、曝光、色调映射或正式模型颜色。

### 8.4 门开关动画：第一期必须导出

**每扇纳入导出的门，都必须包含可独立播放的开门和关门动画。** 只输出门板当前姿态、铰链节点或编辑器内的 JavaScript 旋转逻辑，均不满足要求。动画应随标准 glTF 数据交付，外部播放不依赖本软件的 Rust 后端或编辑器脚本。

建议每扇门生成两个命名片段，例如 `Door_<stableId>_Open` 和 `Door_<stableId>_Close`。名称使用稳定对象标识，不因切换中英文而变化。每个片段仅作用于对应门的铰链节点，不能同时带动其他门、门框、墙体或整个楼层。

建议节点结构为 DoorRoot 下包含固定门框和 HingePivot，门板作为 HingePivot 的子节点。DoorRoot 负责沿墙位置和朝向，HingePivot 的局部原点位于铰链轴线上，动画仅改变其旋转。左右铰链和不同开启方向都应保持正确的支点及旋转方向。

技术约束：glTF 的旋转动画使用局部坐标中的四元数，分量顺序为 XYZW；被动画驱动的节点必须使用 TRS 表达，不能仅保留 matrix。建议以标准旋转关键帧表达铰链动作，并通过 GLTFExporter 的 animations 参数明确提交 AnimationClip；不能依赖导出器自动采集运行时的每帧旋转。[R5][R6]

建议动画以门的关闭姿态为统一基准：Open 从关闭角度到设定打开角度，Close 反向返回。当前角度与动画端点分开保存，导出半开门时不得再次叠加当前旋转。默认打开角度 90°、单程 1 秒、简单匀速插值可作为原型值；具体数值不是已确认限制，不增加关键帧时间轴编辑器。

建议静态节点保留导出瞬间的门姿态，而动画片段保留完整开关端点；播放片段时从片段起始姿态开始。导出使用独立快照，不能为了生成动画而修改正在编辑的门角度、撤销历史或工程脏状态。门移动、宿主墙变化或项目重新打开后，重新导出的轨道仍须绑定正确节点。

标准动画交付与外部交互是两件事：外部加载器可读取动画数据，但“点击哪个对象后播放哪个片段”的事件绑定由使用该模型的应用实现，不作为 glTF 文件自带脚本交付。[R6]

### 8.5 导出验收

导出文件须经过 glTF Validator 校验，错误数为 0，警告逐项评估；该校验器可用于检查格式一致性。[R7]

另外必须在独立加载流程中重新加载并核查外观、单位、资源、材质、支点和动画，不能只以“文件成功写出”或“格式校验通过”作为完成标准。编辑器与外部查看器灯光不同可能造成视觉差异，但不能造成丢图、翻面、错位、错误透明或拓扑缺失。

## 9. 国际化、主题与 UI 基础设施

### 9.1 F-12 英语与简体中文

所有应用自有界面文本进入语言资源，包括菜单、工具提示、属性、单位说明、状态、校验、错误和导出提示。支持英语 en 与简体中文 zh-CN，允许切换并保存偏好。

项目对象 ID、数据字段与材质资源标识不随语言切换改变。用户自己命名的楼层和对象不自动翻译。建议 Rust 返回稳定错误代码与参数，前端负责本地化展示。

系统原生文件对话框中的系统文案可遵循操作系统语言，不承诺覆盖系统自身的本地化行为。

### 9.2 Windows 与 macOS

在两类系统上实际安装并测试核心流程，不仅在普通浏览器中验证。覆盖中文及英文路径、空格路径、文件覆盖确认、窗口缩放、高分屏，以及应用退出后的重新打开。

Windows 常用操作使用 Ctrl，macOS 使用 Command；删除、撤销、保存必须有可见菜单或按钮，不以快捷键作为唯一入口。最低系统版本与 CPU 架构另行确定，不默认承诺所有历史系统。

### 9.3 视觉与交互质量

用清晰的选中反馈、预览和吸附提示帮助操作，不堆叠装饰性动画。错误不能只靠颜色表达。材质缩略图、文字及高亮边界需在常见屏幕缩放下清楚可见。

所有 UI 颜色必须以语义 token 统一管理，由 packages/ui 导出；组件采用 shadcn/ui，亮暗及系统主题按第 9.5–9.7 节实现。尺寸、间距、圆角及新建默认值仍建议集中管理；建筑默认值与 UI 配置分离，不能为共享配置而混在一个包中。

### 9.5 F-14 跟随系统、亮色与暗色主题

**已确认：第一期支持三种可选模式：跟随系统（system）、亮色（light）、暗色（dark）。** 外观设置提供明确文字选项，中英文均完整翻译。默认采用跟随系统；不依靠只有太阳／月亮图标的二态开关代替三态选择。

保存的是用户选择的模式 themeMode；实际生效的 resolvedTheme 仅为 light 或 dark。system 模式下，首次启动读取系统偏好，应用运行期间系统主题改变时立即同步；手动选择 light／dark 后不被系统变化覆盖。重新选择 system 时立刻按当前系统偏好解析，不等待下一次系统事件。

主题偏好跨重启保存。首屏渲染前应用已保存选择与解析结果，避免先亮后暗的明显闪屏；异常偏好回退到 system。应用层统一管理持久化、启动缓存与系统事件的优先级，不能让晚到的设置读取覆盖用户刚完成的切换。shadcn/ui 的 Vite 示例展示三态 ThemeProvider 与系统偏好读取；本项目还必须补齐运行期变化监听、清理和启动行为，不能只复制一次性读取逻辑。[R12]

主题切换只更新语义变量和视口辅助配色，不刷新页面、不重建 Renderer／Scene／Camera、不丢失选择、工具预览或未提交输入，不打断已进行的操作。下拉菜单、弹窗、Tooltip、Toast 等 Portal 内容与根页面同步，不能出现亮色弹窗悬在暗色界面上的状态。

应用自绘的标题栏、滚动条、图标、占位与错误状态也遵循主题。操作系统负责的原生窗口装饰和文件对话框，以平台支持范围为准；不把原生 UI 无法逐项定色视为应用 token 违规，也不能据此省略自有界面的主题支持。

**模型不随主题变色。** 墙面图片、墙缝纯色、楼板、门窗和玻璃等正式材质属于工程数据；用户打开同一个项目，无论 UI 是亮色还是暗色，模型材质值保持不变。视口背景、网格、坐标轴、控制点和选中描边属于编辑辅助显示，可按主题调整；灯光与曝光不跟着 UI 主题改变。

### 9.6 D-02 packages/ui：颜色 token 的唯一来源

**必须在 packages 下创建 ui 包，即 packages/ui。全部应用自有 UI 颜色统一由该包公开导出。** 下文包名 @building/ui 仅为命名示例，实际 scope 可确定后统一替换，但目录职责与单一来源不能改变。

包内区分基础色值与语义 token。业务 UI 只能消费语义 token，不直接选取某个灰阶或某个品牌色；同一语义分别配置 light 和 dark 两套值。原始颜色字面量只允许在 token 源文件中集中定义，生成文件不得手工维护第二份真值。

| token 类别 | 语义示例 | 覆盖范围 |
| --- | --- | --- |
| 基础背景与文本 | background、foreground、muted、muted-foreground | 主界面、说明文字、占位、空状态 |
| 面板与弹出层 | card、popover、sidebar 及各自 foreground | 属性区、楼层列表、弹窗、菜单、提示 |
| 操作与选中 | primary、secondary、accent 及 foreground | 按钮、工具激活、列表选中与悬停 |
| 边界与焦点 | border、input、ring | 分隔、输入框、键盘焦点、控制柄 |
| 状态反馈 | destructive、success、warning、info 及 foreground | 错误、无效操作、成功、警告和提示 |
| 遮罩与细节 | overlay、shadow、disabled、scrollbar | 弹窗遮罩、阴影颜色、禁用状态、滚动条 |
| 三维编辑辅助 | viewport.background、grid、axis、selection、snap、preview | 视口背景、网格、坐标轴、选中、吸附与有效／无效预览 |

语义命名应对齐 shadcn/ui 的 background／foreground 等变量，避免为同一个含义建立两套独立色表。shadcn/ui 官方支持 CSS 变量及语义 token，暗色可通过覆盖同名变量实现。[R13]

**推荐的单源实现：** 在 packages/ui 内以类型化 token 源生成亮暗 CSS 变量，同时导出供非 DOM 代码使用的解析色值与类型。样式入口统一，例如 @building/ui/styles.css；组件、token 和主题分别提供公开子路径，例如 /components/*、/tokens、/theme。必须通过 package exports 访问，不从其他 workspace 穿透相对路径读取 src 内部文件。/tokens 为纯数据与类型入口，不引入 React、DOM 或 Three.js。

应用侧全局 CSS 只组合包样式与布局，不再次定义亮暗色表。Tailwind 的颜色类映射到这些语义变量；允许 bg-background、text-foreground 等语义类，不允许用 bg-zinc-950、text-white、任意 hex 类等直接表达 UI 配色。SVG 使用继承自语义色的 currentColor；渐变色标、阴影、描边、加载骨架等也不能绕过 token。currentColor、inherit、transparent 等表达继承或无填充的结构性值可使用，不以它们隐藏实际硬编码色值。

**Three.js 配色桥接：** 应用集成层在主题解析变化时，从 ui 包取出编辑辅助色并转换为运行时所需的明确色彩空间数值，调用三维运行时的主题接口；不在每帧读取 CSS，不让 editor-core 或 building-geometry 依赖 ui。采用 OKLCH 等 CSS 色值时，应通过统一转换输出运行时支持的 sRGB 值，并按 Three.js 色彩管理约定处理；不能把 var(--token) 或未经兼容验证的 CSS 色串直接交给三维材质。[R14]

图片内容、用户选择的建筑材质颜色及其 UI 色块预览是运行时数据，不是 UI 品牌配色，不强行转换成主题 token。内置建筑材质色值独立放在模型材质预设中，不从当前亮暗主题推导。上述例外应按目录／数据类型登记，不能以“来自数据”为由放行业务组件中写死的 UI 颜色。

提供自动检查：未批准位置出现颜色字面量、直接使用基础调色板、亮暗语义键缺失、生成结果过期或出现重复色表时阻止合并。新增语义必须同时补齐两种主题及对应状态。该检查同样覆盖 packages/ui 内的组件源码，不只检查 apps。

### 9.7 D-03 基础组件采用 shadcn/ui

**已确认：React UI 的基础组件采用 shadcn/ui，并统一进入 packages/ui 管理。** 按需求引入 Button、Input、Select、Dialog、DropdownMenu、Tooltip、Tabs、Slider、Switch、ScrollArea 等，不为凑组件库而安装全部组件。

shadcn/ui 以可修改的组件源码为基础；本项目统一维护共享组件及依赖，再由应用组合成工具栏、楼层面板、属性面板和材质面板。不要在每个功能目录复制一套 Button／Dialog，也不要把墙体业务、工程状态、Three.js 或 Tauri 调用塞进通用 ui 包。[R15]

初始化与后续添加组件时，配置参与 UI 生成的桌面应用和 ui 包的 components.json，确保别名和 CSS 入口指向共享包；启用 CSS 变量模式，采用客户端 React 配置（rsc=false），核对当前版本所需的样式和依赖。shadcn/ui 官方支持通过 workspace 别名把共享组件放入 packages/ui；本项目沿用这一组织能力，不因此强制引入 Next.js、服务端渲染、Turborepo 或在线部署。[R16][R17]

Tailwind 构建需包含共享包源码，生产构建中不能丢失包内使用的样式。新增或更新组件后复核 token、Portal 层级、焦点返回、Esc 行为、中英文长度及亮暗状态；不能原样保留生成源码中的硬编码遮罩或状态颜色。

建筑专用交互可组合通用组件实现。所有 UI 覆盖层优先取得对应输入；打开弹窗或编辑文本时，Delete／Backspace 不得删除场景对象，Esc 优先关闭当前最高层界面或取消其操作，再按工具状态机处理。沿用 Vercel Composition Patterns，避免以大量布尔参数控制一个万能面板。

## 10. 已采纳的架构与实施约束

### 10.1 架构决定：同页面、分模块，不使用 iframe

**采用 React UI + 同页面原生 Three.js + 独立 EditorCore + Rust 文件服务。** 第一阶段为单主窗口、单 Tauri WebView、单主 Canvas。UI 和视口视觉融合，但业务、状态、资源所有权与生命周期分离；不使用 iframe 拆页面，也不采用 react-three-fiber 管理场景。

React 只管理页面布局、普通 UI 和视口容器；ThreeRuntime 管理容器内 Canvas、Renderer、Camera 与 Scene。EditorCore 以普通 TypeScript 实现，不依赖 React、Three.js 场景类、DOM 或 Tauri。Rust 提供本地项目、资源与系统服务，不参与每帧交互往返。

这是本项目的组织选择，不是“R3F 一定更慢”的性能结论。原生 Three.js 与 React 通过明确接口集成；不得用多个互相触发的 React Effect 代替墙体、洞口或 UV 业务流程。React 官方允许通过 Effect 集成非 React 控件，前提是正确处理初始化、更新和清理。[R18]

Tauri 2.0、Three.js、React + TypeScript、Rust 以及 shadcn/ui 为已定路线。具体依赖版本、包管理器和状态库实施时固定；Vite 可作为构建方案，不为架构边界额外引入微前端或服务端。后续更换视口适配技术应形成明确变更，不可在实现中悄悄混用两套场景所有者。

### 10.2 工作区与单向依赖

建议目录如下。packages/ui 为用户明确要求的独立 workspace 包；其他核心模块按下述边界组织为 workspace 包，不要求独立发布到包仓库。

```text

  src/app/                  应用初始化、服务组装
  src/ui/                   建筑业务界面、国际化
  src/integration/          订阅、视口宿主、主题桥接
  src/platform/             Tauri 文件与设置适配
  src-tauri/                Rust 宿主与本地服务
packages/
  ui/                       共享 UI、全部 UI 颜色 token
    src/tokens/             颜色单一来源、类型和解析
    src/styles/             生成的主题 CSS、样式入口
    src/components/         shadcn/ui 共享组件
    src/theme/              ThemeProvider 与主题接口
  editor-core/
    document/               领域模型、版本与查询
    commands/               校验、事务与编辑命令
    history/                撤销重做
    tools/                  与 DOM 无关的工具状态机
  building-geometry/
    walls/ slabs/ openings/ 几何生成与连接
    surfaces/ uv/           面角色和连续纹理
  three-runtime/
    scene/ input/ rendering/ 场景映射、拾取与渲染
    resources/ export/      资源管理与导出场景
```

| 模块 | 职责与允许依赖 | 禁止的反向依赖 |
| --- | --- | --- |
| editor-core | 可序列化建筑数据、命令、查询、事务、历史；普通数学类型 | React、UI 包、Three.js 场景对象、DOM、Tauri |
| building-geometry | 输入领域快照，输出几何、表面角色与 UV；可引用核心类型 | UI、DOM、文件对话框、直接修改文档 |
| three-runtime | Three.js、领域只读数据、几何结果、标准化输入 | React 组件、业务面板、全局 UI Store |
| packages/ui | 通用 React 组件、主题与 token；/tokens 为纯数据入口 | 建筑核心、Three.js、Tauri、本地工程状态 |
| desktop 集成层 | 组装服务、订阅核心、把主题值和命令传给运行时 | 绕过命令随意修改领域对象或 Mesh |
| Rust／platform | 项目与资源 IO、持久化设置、长任务 | 作为第二个可独立修改的实时建筑数据源 |

使用公开 API 和稳定 ID 连接模块，不跨包读取内部对象。通过静态依赖规则阻止循环引用；允许接口先简洁实现，不为每个函数引入事件总线或插件体系。

### 10.3 单一文档源与状态分层

正式建筑数据的唯一来源是 EditorCore 管理的 ProjectDocument。Three.js 场景为其派生视图，React 面板为其查询视图，工程保存与模型导出基于版本明确的快照。

| 状态 | 示例 | 管理与持久化规则 |
| --- | --- | --- |
| 正式工程数据 | 楼层、墙板、洞口、连接、材质、门参数 | 核心通过命令修改；可保存、撤销和导出 |
| 编辑会话状态 | 当前楼层、工具、选中对象／表面、整栋预览 | 独立会话 Store；按需订阅，不混入建筑模型 |
| 高频运行时状态 | 射线、拖动草稿、吸附候选、相机插值、动画进度、GPU 缓存 | 运行时维护，不每帧写工程或触发全局 React 更新 |
| 本机应用设置 | themeMode、语言偏好 | 应用设置服务保存；不随工程迁移、不进入建筑历史 |

React 按面板订阅最小必要字段，保持未变化对象的引用与快照稳定；可使用 useSyncExternalStore 或等价外部 Store 适配。该 API 用于订阅外部数据源，快照必须遵守缓存和一致性要求。[R19]

相机位置、鼠标移动和动画逐帧进度不经过整个 UI Store 或 Tauri IPC。必要的尺寸提示可节流发布给 UI；已经提交的尺寸和最终状态必须精确同步。编辑工具的临时草稿与正式文档有清楚边界，保存不能把半个未完成墙段误写成正式墙。

### 10.4 命令、校验、事务与撤销重做

所有正式建筑修改统一经过 EditorCore 命令入口。UI 属性提交和三维拖拽提交同一种领域命令；禁止 UI 找到 Mesh 后修改 scale，再反推工程数据。

标准路径为“编辑意图 → 命令校验 → 计算关联影响 → 原子提交文档 → 一条历史记录 → 发布变更集 → 更新查询与几何”。墙体长度、高度及厚度变化时，先检查宿主门窗与连接约束；不合法则保留原状态并返回可本地化的错误代码与参数。

一次拖动分为 begin、preview、commit／cancel。pointerdown 记录初值，pointermove 更新临时草稿和可视预览，pointerup 校验后提交一条记录，Esc 恢复初态；预览帧不进入撤销栈。删除楼层或墙体及关联对象是一个可整体撤销的事务。

数值输入中间态（例如尚未输入完整的小数）先留在输入草稿，不按每个字符重建整栋建筑。提交失败保留可修正输入及原工程。文档 revision、异步任务版本及“最后成功保存版本”分别管理；保存旧快照完成时，不能把期间产生的新修改误标为已保存。

### 10.5 领域模型与未来扩展

字段名称可按实现调整，但至少保留以下含义；领域数据不得保存 Mesh、Texture、DOM 或 React 元素。

| 概念 | 必须保留的信息 | 作用 |
| --- | --- | --- |
| Project | schemaVersion、稳定对象集合、资源清单 | 可编辑保存、版本迁移和快照 |
| Level | ID、名称、顺序、标高与层高 | 多层归属 |
| Wall | 端点或连接引用、厚度、高度、楼层、稳定 A/B 身份 | 通用方向与连接扩展 |
| Slab | 轮廓、厚度、楼层、显式高度、用途、上下材质 | 矩形到多边形；楼板与封板统一 |
| Opening | 类型、宿主墙、墙局部位置、洞口宽高 | 门窗与墙体同步 |
| Door | ID、洞口引用、铰链侧、开启方向、当前／端点角度、时长 | 支点、预览与可重建动画 |
| SurfaceBinding | 对象与面身份、材质引用、纯色、平铺参数 | 精确分面赋材质 |
| TextureContinuity | 连续面关系、方向、稳定锚点、收口信息 | UV 连续、重建稳定 |

墙体底层使用通用平面端点与连接拓扑，“仅正交”作为本期工具及校验限制。楼板使用轮廓表达，矩形为四点轮廓的创建方式；未来多边形和楼板洞口通过有版本的数据扩展加入，不推倒文件格式。顶层封板用途和高度显式保存，不按“当前最高楼层”猜测。

采用适合建筑的平面参数加高度表达，不把通用自由建模／完整 CAD 内核作为首期前提。已支持连接仍必须正确处理实体边界，不能仅以相交 Box 的外观近似通过几何验收。

### 10.6 几何输出、表面身份与依赖更新

building-geometry 接收只读快照／局部输入，输出可测试的顶点、法线、索引、UV 和表面分组；可使用 TypedArray，具体精度和容差在实现中集中定义。对象 ID 与面角色稳定，三角形序号不要求重建前后不变。

拾取结果必须从对象与三角形／分组映射回墙 A/B 面、顶底面、端面、洞口内侧或楼板上下表面。材质绑定依赖这些稳定语义，不绑定临时 faceIndex。BufferGeometry 的材质分组可用于实现；每组会形成单独绘制调用，不以“一个 Mesh”假定只有一次绘制。[R3]

根据变更集更新依赖：墙 A 改长时，更新 A、相关连接墙、A 上的门窗，以及受影响的纹理连续路径。后续墙的 UV 起点可能改变，即使几何本身未变；不能只更新被拖动的 Mesh，也不把重建整栋作为默认路径。拓扑变化较大时允许扩大重算范围，但需明确原因和版本。

单独组织连续纹理求解，依据实际可见面连接和方向计算，不假定相邻墙一定 A 接 A。图片资源、表面绑定和连续组分别管理；图片可共享，不意味着每个使用者必须共享相同平铺偏移。内外角实际长度、洞口 UV 保持与闭环策略沿用第 6 节。

### 10.7 ThreeRuntime 的生命周期与渲染调度

ViewportHost 挂载时创建一个三维运行时，卸载时释放。选中对象、切换楼层、打开面板、切换语言或主题均不重建 Renderer／Scene／Camera。模块通过接口表达 setViewportTheme、resize、invalidate、dispose 等能力，接口名不强制固定。

ThreeRuntime 统一拥有渲染循环、事件监听和资源注册；React 不同时管理同一对象的变换。组件清理需注销监听、停止调度、断开尺寸观察并释放不再使用的几何、材质和纹理；共享资源按引用生命周期释放，不提前释放另一对象仍在用的纹理。React 开发 Strict Mode 的额外设置／清理周期必须通过，不能靠关闭它掩盖泄漏。[R18]

采用按需渲染：文档／选择／主题等变化请求一帧；相机运动、拖动和门动画活动期间连续渲染，稳定后停止空转。显式修改对象后必须 invalidate。阴影、DPR、拾取与缓存策略根据基准优化，不提前承诺未经测量的收益。

其他楼层的半透明使用编辑器覆盖状态或派生材质，不能修改共享的正式材质实例。主题与高亮同样为显示覆盖；当多个状态叠加时有确定的优先级。异常几何计算或渲染失败应给出提示，保留可恢复工程，不用过期结果冒充最新显示。

### 10.8 输入路由与工具状态机

三维输入适配层把 DOM 指针事件转换为射线、命中 ID、世界坐标及按键状态；工具状态机只处理标准化输入与编辑意图，不直接持有 DOM 或 WebGL 对象。

输入优先级为“弹窗／文本输入 → 活跃拖动 → 当前建模工具 → 普通选择与相机”。点击 UI 不穿透到 Canvas；拖动开始后正确捕获指针，窗口失焦或取消事件能结束／回滚预览，不留下悬挂事务。

墙体工具明确 Idle、起点已确定、预览、提交和继续绘制状态；门窗工具明确寻找宿主、预览、校验、提交。临时操作相机后回到原工具预览，不丢失起点。非当前楼层在拾取和吸附候选构造时排除，而不只在最终点击回调中拒绝。

快捷键按焦点作用域分发，中英文输入法组合输入期间不触发场景删除／工具快捷键。macOS Command 与触控板路径、Windows Ctrl 与鼠标路径均按第 3、9 节验证。

### 10.9 重计算与异步任务边界

第一期先使用可验证的 TypeScript 几何实现。保留计算后端接口；发现几何重建或批量 UV 计算阻塞界面时，将纯计算移入 Worker，而不是引入 iframe 代替计算线程。Worker 能在独立 worker 执行环境中运行任务；并不负责本项目的 UI 与领域状态所有权。[R20]

任务携带 requestId、项目身份、documentRevision 和对象版本；较旧结果晚到时必须丢弃，切换项目后不能回灌旧项目数据。Transferable 使用后需遵守缓冲区所有权，不把正式文档仍在使用的数组转移为失效对象。出现错误或取消时结束任务状态并保留原工程。

仅在基准证明有必要时引入 Rust／WASM 几何加速；不同时维护多套等价算法，不让每帧相机、门动画和鼠标预览跨 Tauri IPC。测试包括过期结果、并发编辑、取消和保存／导出快照一致性。

### 10.10 保存与独立导出管线

保存：取版本明确的可序列化 ProjectDocument 快照及资源清单，交给平台适配层和 Rust 完成持久化。导出：固定项目版本，获得该版本的完整几何与资源，构建干净的导出场景和门动画，再调用 GLTFExporter；不混合不同版本的缓存结果。

编辑场景和导出场景共享同一几何、UV、材质及门结构构建逻辑，但分别组装对象。导出不直接遍历带有临时透明、主题、高亮和隐藏状态的编辑场景；独立场景不代表维护第二套建模算法。

门结构统一为 DoorRoot 下的固定 Frame 与 HingePivot，门板为支点子节点；节点名称／绑定使用稳定 ID。编辑预览与 Open／Close 片段来自同一参数和动画构建函数。旋转采用 glTF 标准节点旋转轨道，明确通过 animations 参数传给 GLTFExporter。[R5][R6]

动画播放进度不每帧写入工程。播放中保存或导出时，在快照边界采样当时角度，连同完整开关端点生成结果；不把采样过程变成一串撤销记录，也不改变正在编辑的门。导出过程不能为了归零门角度、恢复透明度或换主题而临时修改用户现场。

默认整栋导出保持正式对象，即使其编辑显示暂时隐藏。校验器检查之外，还需独立加载播放；主题差异不能影响材质、UV、支点和动画语义。比较语义一致性，不要求导出文件因元数据或编码顺序而逐字节相同。

### 10.11 Rust、本地资源与文件安全

Rust 负责工程容器、读写与版本校验、资源导入／去重／打包、应用设置和必要后台任务。前端持有正式编辑状态；Rust 不维护一个可独立变更、与前端互相覆盖的建筑状态源。Tauri 通过 WebView 与 Rust 宿主通信，需明确边界。[R1]

GLB 与大资源优先使用可用的二进制传输路径，不把二进制转成巨大 JSON 数字数组或 Base64。Tauri 命令支持 ArrayBuffer／Uint8Array 请求体；这不是零复制承诺，大文件仍需测量峰值内存并按需分块／流式写入。[R21]

文件访问采用最小权限，并检查路径、版本、内容和大小；capabilities 不能代替 Rust 命令内部的校验。[R2] 项目解包防止路径越界，图片解码限制异常资源，保存失败不能损坏上一次有效工程。应用设置的保存失败也应提示，不谎称偏好已经持久化。

Windows 与 macOS 必须在真实 Tauri 宿主中运行核心及主题测试。两平台的 WebView 实现不同，普通 Chrome 测试不能替代桌面验收。[R22]

### 10.12 架构规则、测试与交付证据

将以下规则写入 AGENTS.md 或实际编码工具读取的规则：UI 不直接修改 Mesh／正式文档；正式修改走命令；核心与几何不依赖 React／DOM／Tauri／ui；高频状态不进入全局 React 更新链；导出不读取显示覆盖；同一场景对象和 GPU 资源只有明确所有者；颜色只消费 ui 包公开 token；组件遵循 shadcn/ui 与三项 Skills。

最低测试分层为：无 DOM 的命令／历史／几何／UV 单元测试，Store 与视口适配集成测试，双平台输入／主题／保存的端到端测试，以及独立 glTF 加载播放验证。依赖边界、token 检查和关键回归加入自动化检查；提供有效记录，而不是只添加空脚本。

核心模块、token 子入口需能在不加载 UI 或三维场景的环境中测试。第一期先交付可维护的模块化单体，不要求额外发布 SDK、微服务、多窗口或通用插件系统。

### 11.2 易用性验收建议

让未参与开发、没有专业建模经验的测试者，仅依靠首屏提示完成“一块楼板、四面墙、一扇门、一扇窗、两侧不同贴图、新增第二层、选择是否封顶、保存及含门动画的导出”的任务。

建议目标为：简短引导后，无开发人员现场代操作即可完成；每项失败记录原因及误触路径，而不是只记录总耗时。不能以“熟练开发者知道怎么操作”作为简单易用的证据。

在亮色和暗色下分别执行核心任务，并验证跟随系统变化；覆盖键盘焦点、菜单／弹窗、三维辅助显示和中英文文本。不能仅凭使用了 shadcn/ui 或 Impeccable 就认定易用性已通过。

### 11.3 性能验收建议

建议先建立固定测试工程：3 层、100 段墙、60 个门窗、20 张不同的 2048×2048 图片。该规模是首轮基准建议，不是产品容量上限。

在双方确定的 Windows、macOS 参考硬件及 1920×1080 视口下，建议交互帧率不低于 30 FPS，选择和拖动预览响应 P95 不高于 100 ms。文件读写和图片导入单独记录，不与单帧交互混为一谈。

最低硬件、测试持续时间、具体资源预算和正式性能门槛尚待基准原型确定。进行重复创建、修改、删除、切层和导出测试，检查资源是否随循环持续增长。不得将上述目标写成已经达到的成绩。

## 12. 建议开发顺序与交付物

### 12.1 先验证最容易返工的组合问题

先建立工作区、依赖边界与 packages/ui，安装并验证第 9.4 节的 Skills，写入架构和 token 规则。初始化 shadcn/ui 共享组件、双主题 token 与三态主题控制，先完成 UI 与单 Canvas 的最小集成。

以 frontend-design 建立基于语义 token 的亮暗 UI 方案，按 Composition Patterns 组合 shadcn/ui 完成单层操作，再接入多层、楼板双面与用户控制封板。可运行后以 Impeccable 审查双主题、双语和输入流程，补齐工程可靠性、双平台安装及端到端测试。门动画独立播放与主题不污染导出均在早期验证；开发顺序可调整，已确认范围和架构边界不可省略。

### 12.2 建议交付清单

交付 Windows 与 macOS 可运行版本、源码与构建说明、一个可编辑的两层示例项目，以及包含可独立播放门开关动画的 glTF 2.0 导出样例。示例包含至少两扇不同铰链侧或开启方向的门，并覆盖有封板与移除封板两种状态；不要求楼层实际连通。提供功能、交互、资源迁移、动画播放和导出一致性测试记录。

同时交付三项 Skills 的来源与安装验证、项目 rules、架构决策与依赖说明、UI 设计与 Impeccable 修复记录，以及 React 组件组合审查记录。提供 packages/ui 的公开 API、token 清单／生成说明、shadcn/ui 配置、版本记录，以及主题／颜色／依赖静态检查和 A01–A42 的适用测试结果。

### 13.2 可用于原型的建议默认值

建议以层高 3.0 m、墙高 2.8 m、墙厚 0.2 m、楼板厚 0.2 m、网格吸附 0.1 m 开始；新建门默认关闭，完全打开 90°，开／关单程 1 秒；非当前层参考透明度可先采用约 25%。

这些值仅为原型起点，必须集中配置，允许在需要的属性位置调整。透明度属于编辑器显示状态，不能写入真实建筑材质或污染导出。主题默认采用跟随系统；具体视觉色值由 frontend-design 设计、Impeccable 审查后落入 ui 包的双主题 token，不在业务代码临时选色。
